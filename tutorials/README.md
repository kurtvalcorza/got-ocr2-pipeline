## Conformance notes

- **Standalone carrier (NOTEBOOK_SPEC 2.0 §4):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/got_ocr2_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 8-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating revision, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR3):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition (MOD1–MOD8):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes every entry; `from_pretrained(weights_dir=WEIGHTS_DIR)` loads the verified files with `local_files_only=True` and `trust_remote_code=False` through `AutoModelForImageTextToText`/`AutoProcessor`. The notebook's only external dependencies are the pinned PyPI distributions and the Hub at that revision.
- **Role stages:** `validate_inputs` writes `outputs/got_ocr2_input_manifest.json` with the schema (the two modes, the token budget range, preprocessing, decoding rule), the ceilings, the input's observed mode and size, the request, the verdict, and one recorded rejection finding from the unsupported-mode probe; `evaluation_report` writes `outputs/got_ocr2_evaluation_report.json` — `sample-sanity` with one `character_error_rate` and one `word_error_rate` entry on the synthetic page; `not-measurable` on BYOD (with what labelled data would make the task measurable).
- The default sample is a deterministic 1000×520 notice page rendered in code with Pillow's bundled font — the same page the smoke run used; error rates against text you rendered yourself on a clean white page are sanity evidence for the input contract, forward pass, decoding and stop handling, not an OCR metric. The page digest depends on the Pillow build's bundled font rendering and is printed, not asserted.
- Score semantics (UNC1–UNC4): generated text carries no score, no probability and no correctness signal; the notebook says so before the first recognition and again in the interpretation section, and states that a blank image still produces text (`(0) = 1 +` in the smoke run). The mode and the token budget are caller-owned request parameters exposed as `# @param` values (defaults `plain` and `DEFAULT_MAX_NEW_TOKENS = 1024`) and passed explicitly on every `recognize` call; `truncated` is surfaced and explained. The notebook performs no validation of its own — image, mode and budget are checked only by the pipeline's `validate_inputs`/`recognize` path.
- Ceilings `MIN_IMAGE_SIDE` (16), `MAX_IMAGE_SIDE` (4096), `MAX_NEW_TOKENS` (4096), `DEFAULT_MAX_NEW_TOKENS` (1024), the two `MODES`, `DECODING` and `STOP_STRING` are printed before the model runs.
- CPU is documented as adequate but slow (card-measured 6.7 s load, 11.4 s per 1000×520 page at 154 generated tokens in `plain` mode, 11.8 s in `format` mode); the notebook states that cost scales with the tokens generated and that GPU bfloat16 output need not match CPU float32 output token-for-token.
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
